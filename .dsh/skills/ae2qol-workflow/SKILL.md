# AE2-QoL 工作流程（证据优先 · 先确认再动手）

> 适用范围：工作区 `E:\wzt\MC\modcreater\AE2-QoL-1.7.10-GTNH`（modId `ae2_qof`，GTNH 2.9.0-beta-3 / MC 1.7.10）。
> 本 skill 与 `SystemPrompt.md`、`docs/AGENT_CHECKPOINT.md` 配套；冲突时以本 skill 的**流程**为准，
> 以 `SystemPrompt.md` 的**具体约束**为准。

## 0. 一句话总则

**不清楚问题就不读源码；没有证据就不给方案；没经确认就不改文件。**
宁可多问几轮，也绝不"猜着改、改一点试一点"。

---

## 1. 阶段 0：把问题确认到 99%（提问协议）

### 1.1 目标

用户给的往往是**现象**，不是**问题**。本阶段只做一件事：把现象变成可复现、可验收、边界清晰的问题定义。

### 1.2 99% 的可操作定义（全部满足才算达到）

1. 能用自己的话准确复述每个问题；
2. 能区分并分别写清：**现象 / 预期 / 实际结果 / 复现步骤 / 环境 / 模组版本 / 源码范围**；
3. 能列出所有关键假设，并标明**哪些已确认、哪些未确认**；
4. 能预测每个问题的**验收标准**（含"必须保持不变的现有行为"）；
5. 能说清**不做什么**（避免范围蔓延）。

### 1.3 每轮提问的要求

- **必须用 `ask_user_question` 工具**提问，不要只在正文里问；
- 每轮 4–8 题，每题都要**具体**，并给出**我的猜测 + 置信度**；
- 选项优先给"可判定的分叉"（能一句话决定排查方向的），避免"你还有什么要补充"这类空泛问题；
- 允许**多轮**，不限轮数；发现理解偏差立即停止并回到本阶段。

### 1.4 提问之前，先自己用**只读**手段侦察（不要问自己能查到的事）

| 手段 | 用途 |
|---|---|
| `git log/status/diff` | 真实提交状态、工作区脏净（**不要相信文档里写的"未提交"**） |
| 列实例 `mods/` 与 `logs/` 目录、比对文件时间戳与 SHA256 | 实际部署的是哪个 jar、依赖的真实版本、最近运行时间 |
| 读 `logs/fml-client-latest.log`、`mixin.log` | Mixin 是否真的注入、有无异常 |
| `javap -p -c` 目标 jar | **运行产物的真实成员签名**（优先级高于任何源码） |
| 比对编译期 `libs/` 与运行期实例 | 找出"编译基线 ≠ 运行基线"的依赖 |
| 读 `docs/`、`CHANGELOG.md` | 历史结论（但**可能过期，必须实测核对**） |

> 铁则：**`reference_src` 的源码不等于编译基线**；一切以 jar 字节码与实例实况为准。

### 1.5 本阶段的禁止清单

- 禁止读源码（`.java`）；
- 禁止给修复代码、补丁、diff；
- 禁止给完整实现方案；
- 禁止修改任何文件（含文档）；
- 禁止部署、禁止提交。

### 1.6 解锁口令

只有用户明确说 **「确认理解，开始读源码」**，才进入阶段 1。
（用户若通过选项选择了等价表述，视为已授权。）

## 2. 阶段 1：只读源码取证

### 2.1 证据优先级（从高到低）

1. **运行产物的字节码**（`javap` 实例正在用的 jar）；
2. **实例日志**（真实运行痕迹）；
3. **源码**（注意参考源码可能与 jar 不一致）；
4. **文档**（`CHANGELOG`/`docs/`，可能过期）。

### 2.2 必须产出的「修复思路」要素

每个问题都要写全：

- **可疑点**：候选根因，逐条列出并给置信度；
- **证据**：文件 + 行号 / 字节码片段 / 日志行 / 用户实测数据；
- **调用链**：从入口到失效点的完整路径（类 → 方法 → 行号）；
- **涉及文件/类/方法**：精确到可定位；
- **为什么这样改能解决根因**：要能一句话说通因果；
- **影响范围**：其它通道/槽位/界面/模组兼容性会不会变；
- **风险评估**：失败模式（尤其**静默失效**）与已知差异；
- **验证方法**：可执行的实测步骤 + 验收标准 + 回退方式。

### 2.3 本阶段的纪律

- 禁止"可能是/大概/试试看/先改这里看看"这类猜测式表述；证据不足就**继续提问**或**要求日志/复现/截图**；
- 目标一轮成功；若必须分阶段，先给完整方案与修改点，经确认后再实施；
- 发现理解偏差，立即停止并回到阶段 0。

### 2.4 解锁口令

只有用户明确说 **「确认方案，开始修改」**，才进入阶段 2。
方案中包含**需要用户拍板的产品决策**（如"只修本模组元件还是改通用行为"）时，必须先问清再动手。

## 3. 阶段 2：实施

### 3.1 改动纪律

- 只改本次需求相关代码；**不动无关逻辑**，不顺手重构/格式化；
- 旧注释原样保留；新增注释优先中文，并写清 **Why**；
- 仅删除本次改动产生的无用 import/变量/方法；既有死代码只标记不删除；
- 一个功能/bug 一个 commit；**代码 + 文档 + 版本号放同一个 commit**；
- 不提交构建产物（`build/`、`.gradle`）。

### 3.2 构建与产物核对（硬性）

```powershell
$env:JAVA_HOME = 'E:\java17'          # 系统默认 Java 25 会构建失败
$env:GRADLE_USER_HOME = 'C:\Users\29357\.gradle'
.\gradlew.bat build --offline -x spotlessJavaCheck -x spotlessCheck
```

- **必须用无管道命令复核进程退出码**（本项目管道命令的退出码不可信，文档已记录该坑）；
- 产物在 `build/libs/`，**解包核对**：新增/改动的类与方法确实入包，且名称未被重混淆改名
  （尤其 SRG 名与 Mixin 注入助手）；
- 不要部署 `-dev` / `-sources` 变体。

### 3.3 部署与回滚

- 部署到测试实例**必须单独征得用户同意**；
- ⚠️ **替换前必须先确认游戏/服务端已完全退出**。Windows 下运行中的进程会**锁定** jar：
  此时 `Move-Item` 会失败，导致"旧 jar 没移走 + 新 jar 已复制进来" ⇒ **mods 里同时存在两份同名 mod（重复 modId）**。
  2026-09-25 已实际踩到一次。**一旦发生，立刻把新 jar 移出 mods 恢复一致状态**，再让用户退游戏后重做。
- 顺序固定为：**① 确认进程已退出 → ② 移出旧 jar（不删除）→ ③ 复制新 jar → ④ 比对 SHA256 → ⑤ 确认 mods 里只有一份**；
- ⚠️ **"游戏是否在跑"的判据必须精准**：Gradle 守护进程同样是 `java.exe`，**不能**用"存在 java 进程"当判据
  （2026-09-25 因此误拦一次）。正确判据是命令行含**实例路径**或 `launchwrapper` / `net.minecraft`：
  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='java.exe' OR Name='javaw.exe'" |
    Where-Object { $_.CommandLine -like "*$inst*" -or $_.CommandLine -like '*launchwrapper*' }
  ```
- 替换脚本应把该判据写成**前置中止条件**（命中就 exit，不动 mods），并在最后打印
  「mods 内 AE2-QoL 数量」（必须为 1）与实例/本地 SHA256 比对结果；
- 若游戏仍在运行：**不要动手**，先请用户完全退出；并告知重启后才会加载新 jar（mods 仅在启动时加载）；
- 测试实例始终**只读**，除部署 jar 外不改动实例文件。

## 6. 已踩过的坑位（动手前先扫一遍）

1. **GT jar 未反混淆**：`libs/gregtech-*.jar` 里 MC 接口成员保留 **SRG 名**
   （`IInventory.isItemValidForSlot` → `func_94041_b`）。**用 MCP 名去 `javap` 比对会得出错误结论**；
   在 GT 子类里覆写这类方法必须写 SRG 名。仓库已有先例：`merged/GuiMergedTerminal.java` 的 `func_146977_a`。
2. **`reference_src` ≠ 编译基线**：曾据参考源码断定"5.09.54 新增 CommonMetaTileEntity.isItemValidForSlot"，实为错误。
3. **AE2 包处理器运行在网络线程**（FML `FMLEventChannel` 的 `ServerCustomPacketEvent`）：
   在其中替换 `player.openContainer`／开界面**不会生效**；必须 `scheduleServerTask` 归队服务端 tick 线程。
   "与原版同上下文"不等于"可以开界面"。
4. **AE2 的 IO 端口每个元件只取一个存储通道**：`TileIOPort.getInv` 在 `AEStackTypeRegistry.getAllTypes()`
   （HashMap 顺序）取到第一个匹配就 `break`；多通道元件因此只搬一个通道。
5. **Mixin 静默失效**：target/描述符写错不一定崩溃；以注入日志与产物字节码为准。
6. **静默兜底会掩盖故障**：`catch` 里既不放行也不记日志、或按"最保守"返回，会让功能永久失效且无痕迹；
   核心/网络路径至少 `LOG.warn` 一次（且在热路径上去重，避免刷屏）。
7. **图集 sprite 尺寸 0×0 = 没进图集**：渲染结果是**透明**而非紫黑，不要误判成资源包问题。
8. **MTE 数字 ID 是独占资源**：换号必须配套存档 NBT 迁移，否则旧存档终端配置丢失。
9. **热路径性能**：每次 tick 都会跑的逻辑，要把"只有目标物件存在时才需要"的开销做成懒求值。
10. **启动器参数要按"实际生效值"验证，不能只看配置文件**（2026-09-25 实际踩到）：
    改了 `instance.cfg` 的 `MaxMemAlloc=8192`，实际发出的却是 `-Xmx9192m`（用户随后又在 GUI 里改过），
    而我只用"自己跑 java 命令"验证过参数可接受——**那验证的不是启动器真正发出的命令行**。
    正确做法：从**运行中的进程命令行**核对（`Get-CimInstance Win32_Process` 的 `CommandLine`），
    或读启动器日志（Prism：`%APPDATA%\PrismLauncher\logs\PrismLauncher-*.log`）。
11. **给堆留够系统余量**：判断内存够不够要算总账——
    `堆上限 + Windows(约 3–4 GB) + 后台程序` 必须**明显小于**物理内存，否则系统换页，
    表现为"世界生成/载入永远走不完"（看着像卡死，而且日志还可能是 0 字节）。
    16 GB 机器上 GTNH 2.9 的合理堆是 **4–6 GB**（官方口径），不要按"官方上限 8 GB"去给。
12. **失败后不要在同一个客户端里反复载入世界**：多次失败的载入不会归还内存，
    后续尝试会在"堆已满但活跃集很小"的状态下 OOM——崩溃报告里
    `Memory: 10 MB / 8192 MB up to 8192 MB` 就是这种特征。**每次失败后彻底重启客户端**。
13. **游戏卡住/崩溃时日志可能是 0 字节**（本整合包的日志有缓冲），
    此时应改用：崩溃报告（`crash-reports/`）、存档目录的 `session.lock`/`level.dat` 写入时间、
    以及**进程命令行与内存占用**来判断它走到哪一步、是否在推进。
