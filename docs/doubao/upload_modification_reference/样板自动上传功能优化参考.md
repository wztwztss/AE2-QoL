# 样板自动上传功能优化参考文档

> 数据来源：`docs/dumps/handlers.json`（GTNH 2.9.0-beta-1 游戏内导出，494个NEI配方处理器）
> 涉及文件：`RecipeNameUtil.java`、`ClientRecipeNameUtil.java`、`NeiRecipeCapture.java`、`RecipeMapNameConfig.java`、`recipe_type_names.json`

---

## 一、现有功能分析

### 1.1 自动上传的配方名称识别流程

玩家在NEI查看配方 → 点击`↑`上传按钮 → 系统需要识别这个配方属于哪种机器 → 在供应器选择界面显示中文机器名。

**ClientRecipeNameUtil.captureFromRecipeHandler()** 的识别顺序：
1. 取 `handler.getOverlayIdentifier()` → 如 `gt.recipe.largechemicalreactor`
2. 用此id查映射表（内置47条 + 用户配置`recipe_names.json`）
3. **查不到 → fallback为 `toDisplayString(overlayId)`** → 把 `gt.recipe.largechemicalreactor` 拆成 `gt recipe largechemicalreactor`（英文，不是中文）
4. 只有overlayId为null时才用 `handler.getRecipeName()`

### 1.2 映射表现状

内置映射文件 `src/main/resources/apu/recipe_type_names.json` 只有 **47条**，覆盖：
- 单方块机器：组装机、压缩机、提取机、粉碎机、化学反应釜、电解槽等
- 部分多方块：蒸馏塔、裂化机、装配线、大型化学反应釜、工业高炉、真空冷冻机、内爆压缩机等

**缺口巨大**：多方块机器的工业电解机、工业搅拌机、工业离心机、煮解池、化工厂、细菌培养缸、生物实验室、工业浮选机等全部缺失。

### 1.3 二合一终端搜索框自动搜索逻辑

**NeiRecipeCapture.fillMergedTerminal()** 第95-102行：
```java
if (!data.crafting && recipeMap != null && !recipeMap.isEmpty()) {
    ClientState.lastRecipeMap = recipeMap;
    String resolved = RecipeMapNameConfig.resolveSearchKeyword(recipeMap);
    if (resolved != null && !resolved.equals(recipeMap)) {  // 关键条件
        GuiMergedTerminal.setSearchFieldText(resolved);
    }
}
```

**关键问题**：`!resolved.equals(recipeMap)` 这个条件。
- `resolveSearchKeyword()` 找不到映射时返回原始recipeMap（英文id）
- 此时 `resolved.equals(recipeMap)` 为true，条件不满足
- **搜索框根本不会被填入任何内容**
- 结果：玩家从NEI点`+`转移配方后，搜索框是空的，需要手动输入机器名过滤

## 二、问题根因

| 问题 | 根因 | 影响 |
|------|------|------|
| 大部分机器显示英文id | 映射表只有47条，覆盖率17.6% | 供应器选择界面显示 `gt recipe largechemicalreactor` 而非"大型化学反应釜" |
| 二合一搜索框不自动填 | `!resolved.equals(recipeMap)` 条件在无映射时不满足 | 转移配方后搜索框为空，需手动输入 |
| 用户需手动补配置 | 没有利用NEI已提供的中文名称 | 每次遇到新机器都要手动在`recipe_names.json`里加映射 |

**最核心的发现**：NEI的 `IRecipeHandler.getRecipeName()` 已经返回中文名称（handlers.json的`Handler Recipe Name`字段证实），但现有代码只在overlayId为null时才调用它，优先级最低。

## 三、方案A：Fallback逻辑改进（最小改动）

### 3.1 具体改动

**文件**：`ClientRecipeNameUtil.java` 的 `mapRecipeHandlerToSearchKey()` 方法

**现有逻辑**（第38-68行）：
```java
public static String mapRecipeHandlerToSearchKey(IRecipeHandler handler) {
    // 1. overlayId → 映射表查找
    // 2. 查不到 → toDisplayString(overlayId)  ← 问题在这里
    // 3. overlayId为null → handler.getRecipeName()
    // 4. 最后 → toDisplayString(className)
}
```

**改进后逻辑**：
```java
public static String mapRecipeHandlerToSearchKey(IRecipeHandler handler) {
    // 1. overlayId → 映射表查找（不变）
    // 2. 查不到 → 优先用 handler.getRecipeName()（NEI已提供中文）
    // 3. getRecipeName()也没有 → toDisplayString(overlayId)（最后的英文兜底）
    // 4. overlayId为null → handler.getRecipeName()
    // 5. 最后 → toDisplayString(className)
}
```

具体改动：在第49行 `return toDisplayString(overlayId);` 之前，插入 `handler.getRecipeName()` 的调用。

### 3.2 原因和理由

1. **NEI本身就提供中文名称**：handlers.json证实每个配方处理器都有`Handler Recipe Name`中文字段，`IRecipeHandler.getRecipeName()`直接返回它，不需要额外映射
2. **改动最小**：只改一个方法的fallback顺序，不影响已有映射表的优先级
3. **向后兼容**：已有映射表的47条仍然优先使用，只有查不到时才用NEI的中文名称
4. **覆盖全部mod**：不仅GT，其他mod的配方处理器也有getRecipeName()，一并解决
5. **零配置**：用户不需要手动在`recipe_names.json`里补任何东西

### 3.3 风险和注意事项

- 个别mod的`getRecipeName()`可能返回英文或空字符串，此时仍fallback到`toDisplayString()`，不会更差
- `getRecipeName()`返回的可能是配方类别名（如"合金炉熔铸"）而非机器名，但比英文id好得多
- 建议加日志：当使用getRecipeName()作为fallback时记录一条debug日志，便于排查

## 五、二合一终端搜索框自动搜索优化

### 5.1 现有问题

NeiRecipeCapture.fillMergedTerminal() 第99行：
```java
if (resolved != null && !resolved.equals(recipeMap)) {
    GuiMergedTerminal.setSearchFieldText(resolved);
}
```

当映射表查不到时，`resolveSearchKeyword()`返回原始recipeMap（英文id），`resolved.equals(recipeMap)`为true，**搜索框不填任何内容**。

### 5.2 优化方案

**改动1**：配合方案A，在fillMergedTerminal中直接用handler的中文名称

在extractFrom()中已经有handler对象，可以同时捕获`handler.getRecipeName()`：
```java
// 在extractFrom()中添加
if (!data.crafting) {
    try {
        String cnName = handler.getRecipeName();
        if (cnName != null && !cnName.isEmpty()) {
            ClientState.pendingRecipeCnName = cnName;
        }
    } catch (Throwable ignored) {}
}
```

然后在fillMergedTerminal中：
```java
if (!data.crafting && recipeMap != null && !recipeMap.isEmpty()) {
    ClientState.lastRecipeMap = recipeMap;
    String resolved = RecipeMapNameConfig.resolveSearchKeyword(recipeMap);
    // 优先用映射表中文，其次用NEI的getRecipeName()，最后用原始id
    if (resolved == null || resolved.equals(recipeMap)) {
        resolved = ClientState.pendingRecipeCnName;
    }
    if (resolved != null && !resolved.isEmpty()) {
        GuiMergedTerminal.setSearchFieldText(resolved);
    }
}
```

**改动2**：去掉`!resolved.equals(recipeMap)`条件，只要resolved非空就填

即使resolved是英文id，填入搜索框也比空着好——玩家至少能看到当前配方的id，且部分供应器名称可能包含英文关键词。

### 5.3 原因和理由

1. **用户体验**：转移配方后自动过滤出对应机器的供应器，是二合一终端的核心体验，空搜索框等于功能失效
2. **NEI已提供中文**：handler.getRecipeName()在客户端就能拿到，不需要映射表
3. **英文兜底也比空好**：即使没有中文，填入英文id也能让玩家知道当前配方类型，且搜索框支持模糊匹配
4. **与方案A/B协同**：方案A/B改进了名称识别，搜索框优化确保识别出的名称能正确填入

## 六、实施建议

### 6.1 推荐实施顺序

1. **先做方案A**（改动最小，立即见效）：改ClientRecipeNameUtil的fallback顺序
2. **再做搜索框优化**：改NeiRecipeCapture.fillMergedTerminal，确保中文名称能填入搜索框
3. **最后做方案B**：用267条完整映射表替换47条，提升内置覆盖率

### 6.2 验证方法

1. 进入游戏，打开NEI查看一个未在47条映射中的机器配方（如工业电解机、煮解池）
2. 点击`+`转移到二合一终端，确认搜索框自动填入中文机器名
3. 点击`↑`上传，确认供应器选择界面显示中文机器名
4. 测试多个mod的配方（GT、GT++、BartWorks、gtnhlanth、TST等）

### 6.3 回退方案

- 方案A：如果某个mod的getRecipeName()返回异常值，在映射表中添加该overlayId的正确中文即可覆盖
- 方案B：保留旧的47条映射作为backup，新映射表有问题时随时回退
- 搜索框优化：如果自动填入的名称干扰搜索，可加配置开关控制是否自动填入
