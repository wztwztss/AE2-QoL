# AE2-QoL 单机实测脚本（阶段 2）

原先适用版本：`3.19.0-fix14`；阶段 3 复测适用版本：`3.19.0-fix38`

测试实例：`GT_New_Horizons_2.9.0-beta-1_Java_17-25(1)`，严格只读。除正常启动生成的存档/日志外，不得手动修改实例文件；本轮不部署新 JAR。

## 通用规则

1. 每项先测新建空存档，再测已有旧存档；结果分别回填。
2. 每项记录：通过 / 失败 / 异常 / 不适用，附截图、`fml-client-latest.log` 片段、mixin 日志与 crash-report 编号。
3. 启动后先记录：`[AE2QoL-RFB]`、`[AE2QoL]`、`[APU]`、Mixin 报警、MUI2 `TextWidget` 越界警告。
4. 涉及多玩家风险的场景可在局域网开放世界做最小验证；若无法进行，只填单机结果。
5. 不使用创造模式掩盖权限问题；权限类测试优先使用普通玩家/OP 双账号。
6. F22 在 fix14 构建中未注册（阶段 2 标为「当前不可测」）；阶段 3 已在 fix38 中恢复注册，复测步骤见文末「阶段 3 修复回填」。

### 用户补充实测问题

- F1：自动上传的逻辑仍存在问题，具体场景待用户补充。
- F1 补充：自动上传会传错目标供应器；对工作台合成类配方无法识别目标。
- F1 日志初判：客户端日志显示上传按“记住的供应器名字”匹配当前网络里的机器，`gt.recipe.microwave→熔炉`、`gt.recipe.polarizer→两极磁化机` 均只匹配到 1 台。传错目标需补充完整服务端 `[Upload]` 日志与“预期目标/实际目标”对照。工作台合成类样板编码时写入的是 `crafting` 标记而不是 GT 配方池 ID，现有上传逻辑无法据此定位供应器，属于设计缺口。
- F6 日志初判：完成通知的推送条件是玩家主背包中持有绑定同一 ME 网络的 AE2 无线终端（`INetworkEncodable` 密钥与网络安全站序列号一致）。仅打开方块/面板终端、背包没有该无线终端时不会收到通知。若已持有仍无通知，需要服务端日志确认 `CraftingCompletePacket` 是否发出。
- F14 日志初判：客户端日志无任何 `[AE2QoL] Smart doubling` 或开关写入记录。倍增生效需要：在接口/样板输入仓 GUI 打开倍增开关、配方为处理类（非工作台 craftable）、相邻机器可容纳多轮、CPU 材料充足。需要服务器端完整日志（关键字 `Smart doubling`、`Smart doubling toggle failed`、`hasSmartDoublingTask`）判断开关包是否到达服务端、Mixin 是否注入。
- F5：书签数量与可合成 UI 观感需重新设计。
- F10：无线收发器 UI 需优化；无线连接存在概率性断开。
- F15/F1 关联：合并终端把样板放回去后，读取样板内容会卡一下，需要退出并重新打开才能刷新。
- F17：NEI 中对无限元件按 U 查看内容无效。
- F22：用户尝试恢复注册后游戏崩溃；需要 crash report 与启动日志定位根因。

## F1. NEI 样板上传 / 撤回 / 交换 / OV

前置：AE 网络、ME 控制器、驱动器、样板终端、CPU、供应器；至少准备标准编码样板、终极编码样板、ae2fc 流体样板；开启 NEI 配方页。

用例：

1. 唯一供应器直传：打开配方，点击上传。预期样板进入目标供应器；终端与供应器 GUI 均显示样板。
2. 记忆供应器：同一配方再次上传。预期不再弹选择页，自动发到上次供应器；删除 remembered provider 后应重新弹页。
3. 多供应器手动选：同一配方存在多个供应器。预期选择页显示中文机器名；未命中中文映射时可用原始 ID 或手动映射兜底。
4. 撤回：上传后点撤回。预期取回最近一次匹配样板；连续上传两个后撤回应按后进先出或当前实现语义稳定，不丢样板。
5. 交换：同一配方存在主/副产物两个样板。预期循环交换；无副产物时不交换。
6. OV：点击叠加层开关。预期 GTNL/PH 可用时可开启；不可用或配方不支持时不崩溃，仅无变化或提示。
7. 服务器边界：局域网中由非 OP 普通玩家操作。预期遵循 AE2 权限；无权限时拒绝且不掉样板。
