## 1. 总体结论

### 1.1 结论摘要

4.0.0 之后的主要开发目标已经基本落地，尤其是 4.1.0 的“产线管理器第 1 期”已经形成完整的代码、资源、文档和构建链路，不再是只有设计稿的功能。

但是，当前更准确的判断是：

> **功能实现基本完成，静态质量门槛基本完成，正式发布前的游戏内验收和文档收口尚未完全完成。**

建议将项目状态标记为：

- **代码实现：基本完成**
- **静态审计：已完成主要轮次**
- **构建：通过**
- **自动化测试：不足**
- **游戏内实测：未形成完整证据闭环**
- **UI：可用，但仍有明显的信息层级和操作效率提升空间**
- **正式发布就绪度：约 75%～85%，取决于是否要求真实专用服/存档验收**

### 1.2 4.0.0 之后的核心成果

从 Git 历史看，4.0.0 之后集中完成了以下内容：

1. 产线管理器第 1 期：终端第三页、产线数据模型、存档、采样、汇总、机器绑定、绑定卡、预置产线和 wiki JSON 导入。
2. 真实停机语义：步骤/整线暂停写入 GT 机器的 `disableWorking()`，恢复时调用 `enableWorking()`。
3. ServerUtilities 团队权限和依赖守卫。
4. 7 条预置产线资源与预置选择面板。
5. `start[]` 多形态导入、期望边界持久化、错误逐项反馈。
6. 绑定卡材质、创造页入口、生存合成配方。
7. GuideNH 中英文指南页和索引同步。
8. 多轮静态自审、Spotless 格式检查、构建和 JAR 资源核对。

从变更规模看，4.1.0 相关提交包含约 45 个文件、约 4492 行新增内容，主体功能不是空壳。

### 3.1 明确的问题一：设计文档与实现状态存在过期描述

`docs/PRODUCTION_LINE_MANAGER_DESIGN.md` 的部分章节仍保留“v1 软暂停、不写 GT 机器”的描述，而后面章节已经改成“真停机”。

`CHANGELOG.md` 也存在历史口径与当前版本不完全一致的内容：文件开头仍显示当前版本为 `3.32.0-fix4`，但仓库当前源码和标签已经是 `4.1.0`。

这会导致后续智能体、贡献者和用户误判当前状态。

**建议修改方式：**

- 在设计文档顶部增加“当前实现覆盖矩阵”。
- 对已经被决策替换的旧方案加上“历史方案，不适用于 4.1.0”的标记。
- 将 `CHANGELOG.md` 顶部版本摘要改为 4.1.0，并把旧版本规则放到“历史版本规则”小节。
- 在 README 和交接文档中只保留一个当前版本来源，其他位置引用该来源。

### 3.2 明确的问题二：交接文档过于庞大且混入大量历史会话

`docs/AGENT_CHECKPOINT.md` 超过 1600 行，包含从 3.19.x、3.20.x、3.32.x 到 4.1.0 的大量历史记录，并且存在多处互相矛盾的旧状态，例如：

- 旧段落仍写“软暂停”；
- 旧段落仍写未提交、未部署；
- 旧段落中的版本、产物哈希和当前 HEAD 不一致；
- 同一个文档中出现多个“当前会话元数据”块。

这不影响代码编译，但严重影响智能体交接的可靠性。

**建议修改方式：**

- 顶部只保留一页“当前状态摘要”。
- 历史会话移到 `docs/archive/checkpoints/`，按版本分文件。
- 当前状态只记录：版本、HEAD、工作树、最近构建、未验证项、禁止操作和下一步。
- 每次更新替换当前摘要，不要继续无限追加。

### 3.3 明确的问题三：发布记录中的哈希和当前产物需统一

不同文档和提交记录中出现多个 4.1.0 JAR SHA256 值。它们可能对应不同构建阶段，但当前没有一份“最终发布制品登记表”说明：

- 哪个哈希是最终 JAR
- 是否在 Spotless 之后生成
- 是否与 Git HEAD 一致
- 是否是准备发布的 JAR

**建议修改方式：**

新增 `docs/RELEASE_ARTIFACTS_4.1.0.md`，记录：

- Git commit
- 构建命令
- Java/Gradle 环境
- JAR 文件大小
- SHA256
- 包内版本
- 关键资源是否存在
- 是否经过 spotlessCheck
- 是否已单机验证
- 是否已专服验证

## 4. 发现的问题与优先级

### P0：发布前必须处理

#### P0-1：没有完整游戏内验收闭环

代码和静态检查通过，但 `test` 是 `NO-SOURCE`，文档中的 4.1.0 验收项目仍主要是待实测状态。

**修改建议：**

建立一份 `docs/verification/4.1.0-production-line-gameplay.md`，至少记录：

- 客户端和服务端版本
- GTNH、ServerUtilities、MUI2 版本
- 测试存档和团队准备方式
- 每一条验收步骤
- 预期、实际、截图/日志路径
- 通过/失败/阻塞状态

#### P0-2：真停机逻辑需要验证生命周期安全

4.1.0 已把暂停从“只改状态”切换为直接写 GT 机器停机位。该功能比软暂停更符合需求，但风险也更高：

- 机器是否确实属于当前产线
- 机器被解绑、删线、换团队时是否一定恢复
- 区块卸载后是否会误操作
- 同一台机器被异常重复绑定时是否会互相覆盖
- 服务端重启后暂停状态是否正确重放

**修改建议：**

增加针对“暂停 → 区块卸载 → 重启 → 加载 → 恢复 → 解绑 → 删除”的专用验收链路，并在日志中记录 lineId、stepId 和机器坐标。

### P1：应在下一轮修复或发布前收口

#### P1-1：NEI 配方捕获按钮尚未完成

设计稿目标包含 NEI 逐步导入，但 CHANGELOG 明确记录“NEI 配方捕获按钮仍未做”。当前 wiki JSON 导入可以工作，但不能把“NEI 导入”描述成已完成能力。

**建议：**

- README/玩家指南明确标注“NEI 逐步捕获：未实现”。
- 4.2.0 单独完成 NEI API 取证、捕获按钮、会话目标和专服测试。
- 在完成前不要在功能完成清单中使用“NEI 双通道已完成”。

#### P1-2：重命名/删除整线入口状态不清

设计稿中有重命名、删除整线的 UI 设计，CHANGELOG 历史记录却称子面板入口未挂。当前源码可以看到产线行尾设置按钮，但应通过实际 GUI 确认重命名、删除和二次确认是否完整可达。

**建议：**

- 明确一个入口：产线行尾“设置”。
- 设置面板内固定顺序：重命名、暂停/恢复、删除。
- 删除使用按钮二次确认加聊天确认，显示产线名称和步骤数。
- 增加“删除后机器恢复工作”的明确提示。

#### P1-3：中文 wiki 名称解析仍不完整

玩家指南已经诚实写明：预置产线的部分 AE 存量/累计列可能为空，中文名到注册键解析留到 4.2.0。

这意味着“产线定义”和“机器状态”可用，但“库存/累计统计”不是所有预置条目都可用。

**建议：**

- UI 中对未解析条目显示明确徽标：`未解析`，而不是留白。
- Tooltip 显示原始 wiki 名称、解析失败原因和手动修正入口。
- 4.2.0 使用语言无关注册键优先，中文名只作展示和候选匹配。

#### P1-4：分支切换与汇总口径需要显式提示

设计文档要求分支切换时汇总重算，但历史记录又说明 v1 汇总口径不分 branch，存在设计与实现之间的口径风险。

**建议：**

- 当前版本如果不按分支重算，UI 明示“汇总为整线口径，不随分支过滤”。
- 如果已经按分支重算，增加测试记录，确认累计值不被回溯重写。
- 显示“当前分支”和“统计口径”两个独立字段。

#### P1-5：根目录和 docs 的版本信息不一致

当前 `gradle.properties`、`mcmod.info` 和标签是 4.1.0，但 `CHANGELOG.md` 顶部仍保留旧当前版本文本。这是发布认知风险，不是运行时 bug。

### P2：可以后续优化

- `AGENT_CHECKPOINT.md` 过长，降低交接效率。
- 设计稿和玩家指南之间仍有部分术语不统一，例如“绑定卡”和“候选面板绑定”的主次关系。
- 当前构建存在 Mixin 映射警告，建议为历史兼容项建立清单并逐步减少。
- 4.1.0 主要依赖静态检查和构建日志，建议逐步增加可脱离 Minecraft 的导入器、汇总和序列化测试。
- 未跟踪的 `tools/wiki/watch_release.mjs` 应在发布前处理。

## 5. UI 现状评估

### 5.1 当前实现优点

从 `proline/gui/ProLinePage.java` 和 `StockMonitorTerminalGui.java` 看，当前 UI 已具备以下基础：

- 使用 ModularUI2 的 `Flow`、`PagedWidget`、`DynamicSyncedWidget`、`ListWidget`。
- 产线页接入库存统计终端第三页，入口位置合理。
- 产线列表、步骤列表、汇总列表分区明确。
- 步骤行已经有物品图标、名称、运行/输出信息、删除、高亮、传送等操作位。
- 使用 `GuiTextures.BUTTON_CLEAN` 保持了 AE2/GTNH 风格一致性。
- 动态列表通过同步值重建，避免在客户端直接修改服务端数据。
- 主要文本已经经过语言键处理，中英文资源有对应审计。

因此，UI 不是“不可用”，而是已经完成了功能型第一版。

### 5.2 当前 UI 的主要问题

#### UI-1：信息密度偏高，步骤行同时承载过多信息

当前步骤行在约 336 像素内容宽度里同时放置：

- 图标
- 序号和步骤名
- 运行状态和产物文本
- 删除
- 高亮
- 传送

在中文、长机器名、长物品名和高数量场景下，容易出现截断或难以快速扫描。

#### UI-2：状态颜色层级不够系统

代码中能看到灰色、深灰、紫色等文字颜色，但缺少完整的状态色彩规范。用户需要快速区分：

- 正常运行
- 部分运行
- 空闲
- 已暂停
- 离线
- 未解析
- 权限拒绝
- 采样失败

如果全部依赖文字和 tooltip，扫描效率会降低。

#### UI-3：按钮视觉权重相同

新建、导入、预置、删除、暂停、传送等动作使用相近的按钮样式，危险操作和主操作没有明显区分。

#### UI-4：汇总区域缺少明显的“输入/输出”视觉分组

当前汇总文本列表可以显示内容，但输入、输出、累计、速率、期望边界之间的关系不够醒目。

#### UI-5：错误、未解析和空状态缺少统一的状态卡片

当前很多状态通过普通文本显示。建议为“没有选择产线”“没有步骤”“没有候选机器”“导入失败”“名称未解析”建立统一的空状态组件。

#### UI-6：列表操作缺少批量和筛选能力

当产线步骤数量较多时，用户需要滚动寻找某个步骤。当前版本没有明显的搜索、按状态过滤、按分支过滤之外的快速筛选入口。

## 6. UI 美化与可用性改进方案

以下方案只描述如何改，不在本次报告中直接实施。

### 6.1 第一阶段：不改变数据模型的低风险改进

#### 方案 A：统一状态徽标

为每种状态建立颜色和文字规范：

| 状态 | 建议颜色 | 建议文字 |
|---|---|---|
| 在产 | 深绿色 | `运行中` |
| 部分在产 | 金黄色 | `部分运行` |
| 空闲 | 灰色 | `空闲` |
| 已暂停 | 紫色 | `已暂停` |
| 离线 | 深灰/蓝灰 | `离线` |
| 未解析 | 橙色 | `未解析` |
| 错误 | 深红色 | `错误` |

实现方式：

- 抽出统一的 `statusBadge(...)` 辅助方法。
- 状态徽标使用固定宽度的小按钮或带背景的文本控件。
- 颜色只表达状态，不再让普通字段随机使用多种颜色。
- tooltip 保留完整原因。

#### 方案 B：重排步骤行

建议把步骤行改成两行结构：

```text
[图标] [步骤名 / 机器类型]                 [状态徽标]
       主产物 ×数量 · 运行 n/m · AE 存量     [暂停] [详情]
```

第二行再放：

```text
[高亮] [传送] [绑定/解绑] [删除]
```

这样可以减少一行中连续按钮和文本互相挤压。

实现方式：

- 将当前 `Flow.row()` 改为外层 `Flow.column()`。
- 顶部使用 `Flow.row()` 放图标、标题和状态。
- 底部使用 `Flow.row()` 放统计和动作。
- 保留当前同步结构，不改变服务端协议。

#### 方案 C：区分主按钮、普通按钮和危险按钮

建议：

- 主操作：新建、导入、预置，使用更醒目的颜色或标题栏位置。
- 普通操作：详情、候选机器、高亮、传送，保持中性。
- 危险操作：删除步骤、删除整线，使用暗红色，并显示确认文本。

由于 ModularUI2 资源受限，优先使用已有 `GuiTextures` 和文字颜色，不新增复杂贴图。

#### 方案 D：增加页面标题栏和统计摘要

产线页顶部建议固定显示：

```text
产线管理器       3 条产线 · 12 步骤 · 28 台机器
```

选中某条线后显示：

```text
独居石主线       8 步 · 14/16 台运行 · AE 网络：当前终端
```

这样用户不必在列表和汇总之间来回寻找上下文。

### 6.2 第二阶段：提升操作效率

#### 方案 E：产线列表筛选

增加轻量筛选：

- 全部
- 运行中
- 有问题
- 已暂停
- 无机器

实现方式：客户端维护筛选状态，服务端仍发送完整快照；只在客户端重建列表，不改变数据权限。

#### 方案 F：步骤快速筛选

增加：

- 搜索步骤名
- 只看运行中
- 只看离线
- 只看未绑定
- 只看未解析

步骤数量达到 32 或 64 时，这一功能的收益会非常明显。

#### 方案 G：汇总面板改为分组卡片

建议分成三个区域：

1. 外部输入
2. 末端输出
3. 期望边界 / 预警

每行显示：

```text
[图标] 物品名       累计 1.2M    速率 32k/h
```

对未解析条目显示橙色标记并保留原始名称。

### 6.3 第三阶段：与 4.2.0 配套的 UI 改进

- 速率趋势小图或最近采样箭头。
- 瓶颈步骤红/黄提示。
- 分支切换时显示统计口径变化。
- 期望边界显示“达标/未达标”。
- 机器详情面板显示绑定坐标、最后发现时间、离线天数。
- 导入失败显示可复制的错误摘要。
- 支持导出当前产线诊断信息，方便用户反馈。

## 8. 最终判断

### 已达到的项目预期

- AE2 QoL 仍然保持原有 AE2/GTNH 辅助功能范围。
- 4.1.0 产线管理器已经从设计推进到可构建的功能实现。
- 团队、网络、机器、产物、汇总和持久化的核心模型已经建立。
- 代码、资源、语言、指南和构建文件基本同步。
- 静态审计和格式收口做得比较完整。

### 尚未完全达到的项目预期

- 尚无完整的游戏内实测证据证明所有 4.1.0 验收项通过。
- NEI 逐步捕获仍未完成。
- 中文 wiki 名称解析仍不完整，导致部分库存统计为空。
- 设计稿、CHANGELOG 和交接文档仍存在历史状态混杂。
- UI 已可用，但在信息层级、状态辨识、长文本处理和批量操作方面仍有提升空间。

### 发布建议

如果目标是“开发阶段交付、供熟悉项目的用户测试”，当前版本可以进入实测阶段。

如果目标是“面向普通玩家的正式稳定发布”，建议先完成：

1. 4.1.0 全套游戏内验收；
2. 真停机和权限边界验证；
3. 文档版本统一；
4. 至少完成第一批 UI 可用性改进；
5. 在 README 中明确标注 NEI 捕获和中文名称解析的未完成范围。
